# 08 · Accesibilidad (WCAG 2.2 AA)

> Documento: **DS-A11Y-001** · Status: ACTIVE · 2026-10-08
> Código: `components/` · Regla: **nunca** `outline: none` sin reemplazo visible.

Checklist de accesibilidad que todo componente `ds-*` y toda composición de página debe
cumplir. Referencia: WCAG 2.2 AA.

---

## 1. Criterios transversales

### Focus visible (2.4.7)
- Todo elemento interactivo muestra foco visible. **Nunca** `outline: none` sin un reemplazo
  visible (borde, anillo, sombra) que cumpla contraste.
- El orden de foco sigue el orden visual/DOM (2.4.3).

### Tamaño de objetivo (2.5.8 / 2.5.5)
- Objetivos táctiles ≥ 24px (AA 2.5.8, WCAG 2.2) y, donde el layout lo permita, ≥ 32px.
- Los controles compactos (iconos solos) tienen un área de click ≥ su `min-width/height` del token.

### Contraste (1.4.3 / 1.4.11)
- Texto ≥ 4.5:1 (grande ≥ 3:1). Elementos de interfaz y borde de controles ≥ 3:1.
- Los tokens de estado (`--ds-status-*`) ya traen pareja `-on` de alto contraste: úsala para
  texto sobre superficie de estado.

### Teclado (2.1.1)
- Todo interactivo es operativo con teclado (Tab/Enter/Escape). Nada requiere hover para ser usable.
- Modales/overlays: foco entra al abrir, se atrapa (loop) y vuelve al elemento de origen al cerrar.
- Gestos/arrastres siempre tienen alternativa de teclado.

### ARIA (4.1.2 / 1.3.1)
- Usar semántica nativa antes que `role` inventado.
- `aria-label`/`aria-labelledby` en controles sin texto visible (iconos, icon-buttons).
- `aria-expanded`, `aria-selected`, `aria-current` en menús/tabs/paginación.
- Estados activos: `[disabled]` real + `aria-disabled` cuando no sea un control nativo.

## 2. Por familia de componente

| Familia | Requisitos específicos |
|---|---|
| **Form** | Cada `ds-form-field` expone `describedBy` (id del hint/error activo). Los errores se asocian al control (`aria-describedby`) y se anuncian al aparecer. El border por `state` nunca es la única señal (texto/icono acompañan) |
| **Button / actions** | Roles nativos (`<button>`), focus visible, objetivo ≥ tamaño mínimo del token |
| **Badge** | Los tonos se acompañan de texto (nunca solo color). `data-field` para hooks de test |
| **Modal / panels** | Loop de foco, `role="dialog"` + `aria-modal`, Escape cierra, foco vuelve al origen |
| **Toast / notification / banner** | Anunciados (`aria-live="polite"`, errores `assertive`), auto-dismiss con pausa suficiente para leer |
| **Tabs** | Patrón tabs de ARIA (`tablist`/`tab`/`tabpanel`, flechas), `aria-selected` |
| **Nav / menu / breadcrumb / pagination** | Navegación con flechas en menús, `aria-current="page"`, labels descriptivas |
| **Chart** | Resumen accesible: `aria-label` en `ds-chart` + leyenda textual; alternativas tabulares cuando aplique |
| **Table** | Cabeceras asociadas (`scope`/`headers`), caption descriptivo |
| **ds-container** | Roles estructurales por `data-name` (header/aside/body/footer) y landmarks (`banner`, `complementary`, `main`, `contentinfo`) cuando corresponda |

## 3. Checklist rápido (pre-commit)

- [ ] ¿Foco visible en todos los interactivos? (sin `outline:none` huérfano)
- [ ] ¿El target mide ≥ token de tamaño mínimo?
- [ ] ¿Texto con contraste ≥ 4.5:1 sobre superficies y estados?
- [ ] ¿Todo lo operable con teclado?
- [ ] ¿Controles sin texto visible tienen `aria-label`?
- [ ] ¿Overlays atrapan foco y lo restauran al cerrar?
- [ ] ¿Los errores de formulario se asocian al campo y se anuncian?
- [ ] ¿Los mensajes dinámicos usan `aria-live` adecuado?
- [ ] ¿El color nunca es la única señal de estado?

---

## 4. Reglas (MUST)

- No introducir un componente que no cumpla esta checklist.
- El status quo es la línea base: las regresiones de foco/teclado/ARIA se tratan como bugs.
- El design-mode del FAB puede marcar colores hardcodeados y estados problemáticos:
  úsalo como apoyo de auditoría (ver [06-fab.md](./06-fab.md)).
