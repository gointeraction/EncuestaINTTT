Guía de Arquitectura: El Corazón Tecnológico de la Encuesta "Visión Cero"¡Bienvenido, ingeniero! Como mentor en este camino de la arquitectura de sistemas, quiero que visualices este proyecto no solo como una aplicación web, sino como una obra de ingeniería de alta precisión. Imagina que debemos construir una fortaleza moderna capaz de recibir a un millón de ciudadanos en solo 15 días. No se trata solo de abrir una puerta; se trata de garantizar que cada una de esas personas entre de forma fluida, que sus datos estén blindados en una cámara acorazada y que la estructura no ceda ante picos de tráfico masivos.Ese es el desafío de la encuesta "Visión Cero" del INTT. Para lograrlo, hemos diseñado una infraestructura resiliente donde cada decisión técnica, desde el manejo de la memoria hasta la segmentación de red, tiene un propósito vital: transformar la recolección masiva de datos en un proceso rápido, seguro y transparente.1. El Desafío en Números: ¿Por qué necesitamos una súper estructura?Cuando proyectamos recibir un millón de encuestas en un periodo tan breve, el hardware y el software convencionales quedan obsoletos. Para dimensionar esta "fortaleza", hemos consolidado una infraestructura total de 26 vCPUs y 60 GB de RAM, distribuidos estratégicamente para absorber el impacto de la concurrencia.Métrica de CargaValor ObjetivoVolumen total de encuestas1,000,000 finalizadas en 15 díasVisitantes totales estimados2,000,000 a 3,000,000Picos de transacciones (TPS)30 a 50 envíos por segundoSolicitudes HTTP (RPS)350 a 600 solicitudes por segundo¿Qué significa esto para el servidor? En un entorno común, 600 peticiones por segundo saturarían la cola de procesos, provocando caídas. Aquí, "grokkeamos" el problema dividiendo la carga: mientras el servidor web filtra el ruido, el cluster de aplicación procesa la lógica y la base de datos se mantiene fresca operando casi exclusivamente sobre memoria. Esta configuración no es opcional; es la diferencia entre un sistema que sirve al pueblo y uno que colapsa ante él.Con el peso del tráfico calculado, la infraestructura no se levanta como un bloque monolítico, sino como una serie de capas concéntricas diseñadas para la defensa y la eficiencia.2. La Estrategia de "Zonas de Seguridad": El Modelo de Capas (VLANs)Como arquitectos, nuestra prioridad es el aislamiento. Por ello, hemos segmentado la red en cuatro zonas lógicas (VLANs), asegurando que el corazón del sistema nunca esté expuesto directamente al exterior:Zona 1: DMZ Pública (VLAN 10 - Web & Proxy)Componentes: Nginx optimizado.Función Vital: Es nuestro "escudo perimetral". Aquí realizamos la terminación SSL, la compresión Gzip para ahorrar ancho de banda y aplicamos un Rate Limiting estricto (10 req/min por IP) para mitigar ataques de denegación de servicio.Zona 2: Red de Aplicación Interna (VLAN 20 - App Cluster)Componentes: Cluster de Next.js en modo Standalone.Función Vital: Aquí reside el "cerebro". Al usar el modo Standalone, reducimos el peso del despliegue y optimizamos el consumo de recursos, permitiendo que la lógica de las 55+ preguntas fluya sin fricción.Zona 3: Red de Datos Aislada (VLAN 30 - Persistencia & Cache)Componentes: PostgreSQL 16 y Redis.Función Vital: El "búnker". Esta zona no tiene salida a Internet. Una decisión técnica maestra aquí es la asignación de 24 GB de RAM a la base de datos: esto permite que el millón de registros (~2 GB) y sus índices (~600 MB) residan totalmente en memoria, eliminando el cuello de botella del disco.Con las habitaciones de nuestra fortaleza definidas, es momento de analizar las herramientas de alto rendimiento que dan vida a cada capa.3. El Stack Tecnológico: Las Herramientas de Alto RendimientoSeleccionar el stack no es cuestión de moda, sino de capacidad transaccional y flexibilidad.Frontend & Backend:Next.js 16 (Standalone Mode): Elegido por su capacidad de generar interfaces ultrarrápidas y un backend ligero. El modo standalone es vital: permite un despliegue optimizado que solo incluye los archivos necesarios para producción.PM2 (Modo Cluster): Es el motor de alta disponibilidad. Permite el "Zero-Downtime Reload", lo que significa que podemos actualizar el sistema sin desconectar a un solo usuario, aprovechando todos los núcleos de las vCPUs disponibles.Base de Datos:PostgreSQL 16: Seleccionado por su robustez transaccional (ACID). Para este proyecto, utilizamos el tipo de almacenamiento JSON (@db.Text) en el campo de respuestas; esto nos da la flexibilidad de manejar un formulario dinámico de más de 55 preguntas sin la rigidez de un esquema tradicional, manteniendo una velocidad de escritura asombrosa.Seguridad:Redis: Nuestra memoria de corto plazo para gestionar el estado de las sesiones y los límites de tráfico en milisegundos.Tener las mejores herramientas carece de sentido si no implementamos un modelo de defensa que detenga a los intrusos antes de que toquen el primer bit de datos.4. El Escudo Protector: Seguridad en 4 Capas ConcéntricasHemos implementado un modelo de defensa en profundidad donde cada petición debe superar cuatro pruebas de fuego:1. Nginx (Perímetro): Filtra el tráfico masivo y aplica el límite de 10 peticiones por minuto para evitar que scripts automatizados inunden el sistema.2. Cloudflare Turnstile (Capa Anti-Bot): A diferencia de los captchas tradicionales, Turnstile realiza una verificación server-side (API-to-API). El servidor de aplicación valida el token directamente con Cloudflare, garantizando que el usuario es humano sin interrumpir su experiencia.3. Honeypot (Trampa de Miel): Es la primera validación dentro de la lógica de nuestra aplicación. Un campo invisible para humanos pero irresistible para bots; si se rellena, la petición se descarta instantáneamente.4. VLAN Privada: El búnker final. Los datos están en la VLAN 30, físicamente aislados del tráfico público de la VLAN 10.Flujo de Envío: Cuando un ciudadano hace clic en "Enviar", la petición llega a Nginx (Rate Limit) -> la lógica de la App verifica el Honeypot (Detección inmediata) -> se valida el token Turnstile contra Cloudflare (Server-side) -> y solo entonces, los datos se escriben en la base de datos protegida.Con la seguridad garantizada, el último reto es procesar esa montaña de información para que sea útil en tiempo real.5. Analítica Inteligente: ¿Cómo ver un millón de datos en milisegundos?Consultar un millón de registros para generar gráficos en tiempo real es una receta para el desastre en términos de memoria. Por ello, aplicamos el patrón CQRS (Sumarización Desacoplada).Modelo Tradicional (Lento)Modelo de Sumarización (Rápido)Escanea 1,000,000 de filas en cada carga.Lee una sola fila pre-calculada.Tarda hasta 45 segundos ($O(n)$).Tarda menos de 5 milisegundos ($O(1)$).Consume ~2.5 GB de RAM por consulta.Consume solo 8.6 KB de RAM.La clave del éxito: Utilizamos una tabla especial llamada SurveySummary. Esta tabla contiene un único registro (id: 'latest') que almacena todos los indicadores ya calculados. Para mantener los datos frescos, un Cron Job se ejecuta cada hora durante la campaña activa, realizando el trabajo pesado en segundo plano. Así, cuando un directivo abre el dashboard con 46 indicadores, el sistema solo entrega ese registro pre-agregado de forma instantánea.Esta eficiencia permite que el INTT tome decisiones basadas en datos reales, sin poner en riesgo la estabilidad de la recolección ciudadana.6.
